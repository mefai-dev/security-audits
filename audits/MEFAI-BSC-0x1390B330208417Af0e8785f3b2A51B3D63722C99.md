## 3. Architecture Analysis

The contract inherits OpenZeppelin ERC20 v5.6.1 and adds one constant and one constructor.
It does not inherit `Ownable`, `Pausable`, `AccessControl`, or any proxy pattern.

- **Fixed supply.** 564,249,705 tokens are minted once, in the constructor. No `mint`
  function exists in the ABI. Supply can never increase.
- **No ownership.** `Ownable` is never inherited. There is no `owner()`, no
  `onlyOwner` modifier, no `transferOwnership`, and no `renounceOwnership`. Ownership
  is not renounced after the fact - it is never created in the first place.
- **No transfer fee.** No fee logic exists anywhere in the contract. `transfer` and
  `transferFrom` move the exact amount supplied by the caller.
- **No proxy.** The contract is not upgradeable. The deployed code is permanent.
- **No blacklist, pause, or transfer limit.** No mechanism exists to freeze, seize,
  block, or throttle any transfer, for any address, under any condition.
- **No BNB acceptance.** The contract declares neither `receive()` nor `fallback()`.
  A plain BNB transfer to the contract reverts at the EVM level.

**Dependency chain:** OpenZeppelin v5.6.1 ERC20 -> MEFAI

### Complete ABI surface

Ten functions and two events. There are no others.

```
INITIAL_SUPPLY()   allowance()   approve()   balanceOf()   decimals()
name()             symbol()      totalSupply()   transfer()   transferFrom()

event Transfer(address indexed from, address indexed to, uint256 value)
event Approval(address indexed owner, address indexed spender, uint256 value)
```

The absence of `mint`, `burn`, `pause`, `blacklist`, `setFee`, `owner`, and
`transferOwnership` from this list is the substance of this report. Those functions are
not restricted or disabled; they were never written.

## 5. Findings

No critical, high, medium, or low severity findings were identified. Six informational
findings are recorded below. Five are positive security properties; one is a
distribution disclosure that holders should read.

### Finding #1: Initial Distribution is Fully Centralized (Informational - Disclosure)

**Severity:** Informational
**Status:** Disclosure - not a code defect

The constructor mints 100% of the supply to the deploying address. At block one, a single
externally owned account holds all 564,249,705 tokens.

This is a property of the distribution, not of the code, and it cannot be addressed in the
contract: any fixed-supply token must mint its supply somewhere. It is disclosed here
because it is the single largest risk factor a holder should evaluate, and because no
on-chain mechanism constrains what that address subsequently does with the supply.

Holders should independently verify, on-chain:

- the current balance distribution of the token,
- the amount of supply committed to liquidity,
- whether the liquidity position is locked, and for how long.

The audit makes no claim about the deployer's intentions. It states only that the code
grants the deployer no special powers after deployment: the deploying address is, from
block one onward, an ordinary holder with exactly the same capabilities as any other
address.

---

### Finding #2: No Ownership Role Exists (Informational - Positive)

**Severity:** Informational
**Status:** Positive Security Feature

The contract does not inherit `Ownable`. There is no `owner()` function, no privileged
modifier, and no administrative entry point of any kind.

This is materially stronger than a renounced ownership. A renounced contract contains
privileged code paths that are disabled because the owner slot holds the zero address; the
code is still present, and reasoning about it requires verifying the owner slot. Here there
are no privileged code paths to disable. The property holds by construction and requires no
on-chain check to confirm.

---

### Finding #3: No Transfer Fee (Informational - Positive)

**Severity:** Informational
**Status:** Positive Security Feature

No fee, tax, or reflection logic exists. `transfer(to, 1000e18)` credits the recipient
exactly `1000e18` and emits exactly one `Transfer` event.

Practical consequence: the token requires no special handling from DEX routers,
aggregators, bridges, or accounting software. Integrations that break on fee-on-transfer
tokens work with this token unmodified.

---

### Finding #4: No Pause, Blacklist, or Transfer Limit (Informational - Positive)

**Severity:** Informational
**Status:** Positive Security Feature

The contract contains no mechanism to halt transfers, restrict an address, or cap a
transfer amount. No party - including the deployer - can prevent any holder from moving
their balance at any time.

---

### Finding #5: Standard ERC20 Approve Race Condition (Informational)

**Severity:** Informational
**Status:** Inherent to the ERC20 standard

The token inherits the well-documented ERC20 approval race, in which changing a non-zero
allowance to another non-zero value can, under adverse transaction ordering, allow a
spender to transfer both amounts. This is a property of the ERC20 standard itself and is
present in every compliant implementation. The mitigation is the standard one: set an
allowance to zero before setting it to a new value, or use an interface that does so.

---

### Finding #6: Tokens Sent to the Contract Are Unrecoverable (Informational)

**Severity:** Informational
**Status:** By Design

The contract has no rescue or sweep function. Any BEP20 token transferred to the contract
address is permanently inaccessible. This is a direct and accepted consequence of having no
ownership role: a rescue function would require a privileged caller, which would reintroduce
exactly the centralization this design removes.

BNB is not affected. With no `receive` or `fallback` function, a plain BNB transfer to the
contract reverts rather than succeeding, so BNB cannot be stranded this way.

| Property | Value |

| Optimizer | Enabled, 200 runs |

| Yul IR pipeline | Disabled |
| Constructor arguments | None |
| Creation bytecode | 2,814 bytes |
| Deployed runtime bytecode | 1,855 bytes |

Recompiling the verified source with the settings above reproduces the deployed runtime
bytecode exactly, excluding the trailing CBOR metadata section, whose hash depends on the
source file path and is expected to differ between build environments.

`paris` was selected deliberately over the compiler default for this version. The default
emits the `PUSH0` opcode, which is not supported by every BNB Chain execution client and
tooling path in use. The deployed bytecode contains no `PUSH0`.
