## Why This Report Exists

CARV markets itself as a modular data layer for gaming and AI, with a bundle of flagship claims: CARV ID, the D.A.T.A. framework, a verifier node network with TEE and ZK attestation, a CARV SVM chain, and a CARV token that pays gas and powers vote escrow staking. Those are strong, specific, technical claims. A token being live tells a buyer almost nothing about whether the surrounding data layer is real software or a slide deck. This report separates two questions that marketing blends together: is the ERC20 a clean token (yes, it is a plain omnichain OFT), and are the data layer claims backed by code that does what is described. We read the actual public source in the carv-protocol organization and the live Ethereum state, then labelled each flagship claim CONFIRMED IN CODE, OVERSTATED, or FALSE against a file and line.

## Method

Read only, public sources only. Steps taken:

1. Cloned the primary carv-protocol repositories: `d.a.t.a`, `verifier`, `contracts`, `carv-contracts`, `carv-id-sdk`, `plugin-d.a.t.a`, and `solana-oft-example`.

3. Read the CARV documentation corpus at docs.carv.io (including the machine readable llms-full.txt and sitemap.md) for the marketing claims, and quoted the exact language.
4. Cross checked each doc claim against the source and the on chain state.

These are not carv-protocol repositories, so they were excluded from any CARV attribution; none of the findings below rest on them.

## The Foundation: a clean omnichain OFT, a real verifier network, forward looking chain marketing

The CARV ERC20 is the least interesting and safest part of the system, which is a good thing. On chain it resolves to name and symbol CARV, 18 decimals, and an Ethereum chain supply of 262,382,849.079123 CARV. It answers the LayerZero OFT interface: `endpoint()` returns the canonical LayerZero EndpointV2 (`0x1a44076050125825900e736c501f859c50fe728c`), `oftVersion()` returns interface id `0x02e49c2c` with version 1, and `token()` returns the contract's own address, which marks it as a native mint and burn OFT rather than a lockbox adapter. The source confirms this exactly: `CarvToken` is nothing more than a LayerZero OFT with a one time constructor mint.

The substance of the project sits in two other places: the `verifier` Go node and the Solidity in the `contracts` repository (updated as recently as 2026-04-03). Both contain real, non trivial code. The gap between CARV's marketing and its code is not that the code is fake; it is that the marketing describes a finished state (a mainnet SVM chain, ZK attestation, CARV as gas) that the shipped code has not reached. The claims below walk that gap.

## Claim 1: CARV is a live omnichain LayerZero OFT

CLAIM. CARV is an omnichain token deployed across Ethereum, Base, BNB, Arbitrum, Linea, and Solana via LayerZero.

REALITY. CONFIRMED IN CODE and on chain. The Ethereum contract is a canonical LayerZero OFT V2. The source is a thin wrapper, and the repository carries deployment scripts for exactly the advertised chains. The token holds no hidden powers: there is no public `mint` (a raw `mint` call reverts), it is not pausable (`paused` reverts, the selector is absent), and ownership is held by a contract rather than a bare private key.

EVIDENCE.
- `contracts/contracts/CarvToken.sol:6-16`: `import { OFT } from "@layerzerolabs/lz-evm-oapp-v2/contracts/oft/OFT.sol";` and `contract CarvToken is OFT { constructor(... uint256 mintAmount) OFT(...) Ownable(msg.sender) { _mint(msg.sender, mintAmount); } }`.
- On chain: `endpoint() = 0x1a44076050125825900e736c501f859c50fe728c`, `oftVersion() = (0x02e49c2c, 1)`, `token() = self`, `mint(...)` reverts, `owner() = 0xb731...14a9` (code size 171 bytes, a contract).
- `contracts/oft_scripts/` contains `ethereum`, `base`, `bnbchain`, `arbitrum`, `linea`, and `solana` subfolders.

IMPACT. Positive. The token itself is standard, low risk, and matches the omnichain claim. Supply is not inflatable through an owner `mint`, and cross chain movement is governed by LayerZero mint and burn.

## Claim 2 and 3: verifier nodes really check TEE attestations

CLAIM. From the docs: "TEE nodes submit the data verification, AI model training result and the TEE attestation to smart contracts," and verifier nodes "assess the authenticity of the attestation." From the `verifier` README: "these nodes primarily check TEE attestations on chain."

REALITY. CONFIRMED IN CODE. This is the strongest part of the project. The `verifier` repository ships a genuine Intel SGX DCAP quote verifier: it parses the SGX quote header and enclave report, validates the ECDSA signature and the PCK certificate chain using real Intel SGX X.509 object identifiers, and checks the TCB and enclave identity status. The on chain side matches the described protocol precisely: a privileged reporter with `TEE_ROLE` posts attestations, a Chainlink VRF draws a subset of nodes to verify, each selected node submits Valid, Invalid, or Malicious, and an attestation is settled by majority. Nodes that fail to verify can be slashed and rewarded node operators are paid from a Vault.

EVIDENCE.
- `verifier/pkg/dcap/quote.go:22`: `func (q *Quote) VerifyQuote(...)` validating header and enclave report; `verifier/pkg/dcap/cert.go:14-24` carries the Intel SGX OIDs `1.2.840.113741.1.13.1.2.*`; `verifier/pkg/dcap/verify.go:13` `func VerifyAttestation(...)`; `verifier/pkg/dcap/tcb.go` and `enclave.go` implement TCB and enclave identity status (for example `SGX_ENCLAVE_REPORT_ISVSVN_REVOKED`).
- `contracts/contracts/ProtocolService.sol:77` `teeReportAttestations(...) external onlyRole(TEE_ROLE)`; `:95` `fulfillRandomWords(...)` picks verifiers by VRF; `:256` `nodeReportVerification(bytes32 attestationID, uint32 index, AttestationResult result)`; `:203` `nodeSlash(...) onlyRole(SLASH_ROLE)`; rewards via `IVault(vault).rewardsWithdraw(...)` at `:199`.
- `verifier/configs/config.yaml`: the live network target is `chain_id: 42161` (Arbitrum), `contract.addr: 0xa91fF8b606BA57D8c6638Dd8CF3FC7eB15a9c634`, `contract.tee_addr: 0x8A5614...`.

IMPACT. Positive, with a centralization caveat. TEE attestation is not marketing; it is implemented and deployed. The caveats: the attestation source is a single `TEE_ROLE` address, node verification transactions are relayed through a centralized gasless service (`gasless_service.url: https://protocol-api.carv.io`), and the ProtocolService is an upgradeable proxy with privileged admin, slash, and settings roles. The trust model is real but not trustless.

## Claim 4: verifier nodes verify ZK proofs from a CARV zkVM

CLAIM. Aggregated documentation states nodes work by "verifying zk-proofs generated through CARV's zkVM and ensuring TEE attestations," pairing "zk-technology and trusted execution environments (TEE)."

REALITY. OVERSTATED. There is no zero knowledge code anywhere in the carv-protocol source. A full text search across the `verifier` and `contracts` repositories for zk, zkVM, zero knowledge, groth, snark, plonk, halo2, risc0, and sp1 returns nothing in implementation code. The only randomness or proof primitive in the contracts is Chainlink VRF, which is a verifiable random function used to select verifiers, not a zero knowledge proof system. The detailed verifier documentation page itself describes only TEE and SGX and never mentions ZK. The ZK language appears only in higher level aggregate marketing.

EVIDENCE.
- Keyword search over `verifier/` for ZK terms: only hits are the letters inside unrelated identifiers; no zkVM, no proof verifier.
- `contracts/contracts/CarvVrf.sol:4-10`: `import {VRFConsumerBaseV2Plus} ...` and `contract CarvVrf is VRFConsumerBaseV2Plus` (Chainlink VRF, not ZK).
- docs.carv.io how-do-verifier-nodes-work page: mentions TEE and "SGX Attestation Verification" and no ZK.

IMPACT. Medium. A buyer told that nodes verify zkVM proofs is being sold a capability that the open source does not contain. TEE is real; the ZK half of the "zk plus TEE" pairing is, at best, unshipped.

## Claim 5: veCARV staking and CARV token utility

CLAIM. From the docs: "CARV can be converted to veCARV(s) with 1:1 ratio through staking," used for "CARV Protocol governance (voting & delegation)" and to incentivize node operators.

REALITY. CONFIRMED IN CODE. The `contracts` repository implements a vote escrow system. `veCarvToken` is a role gated, effectively non transferable ERC20 that mints on deposit and burns on a time locked withdraw with a claim ratio schedule. `veCarvs` is a Curve style vote escrow staking contract with epochs, lock durations, reward weights, positions, and a reward token distribution. CARV also buys verifier node licenses (as NFTs) directly in the `NodeSale` contract, priced in USD through an oracle and payable in CARV, and node rewards are paid in CARV from the Vault. Governance is implemented with `CarvGovernor` and `CarvVotes`.

EVIDENCE.
- `contracts/contracts/veCarvToken.sol:9` `contract veCarvToken is AccessControl, ERC20, Multicall, IveCarv`; `:33` `deposit(...) onlyRole(DEPOSITOR_ROLE)`; `:39` `withdraw(uint256 amount, uint256 duration)`; `:64` `claim(...)`; transfers gated by `TRANSFER_ROLE` at `:87`.
- `contracts/contracts/staking/veCarvs.sol:10` `contract veCarvs is Settings, AccessControlUpgradeable, MulticallUpgradeable, IveCarvs`; `:64` `deposit(uint256 amount, uint256 duration)`; `:57` `depositRewardToken(...)`; `:93` `claim(...)`; epoch and share math at `:169-178`.
- `contracts/contracts/node_sale/NodeSale.sol:64-77`: `purchase(...)` accepts `Payment.Carv` and transfers CARV from the buyer; `:22` `carvToken`, `:23` `carvNft`.

IMPACT. Positive. CARV has genuine on chain utility today: staking to veCARV, node license purchase, node reward payout, and governance. This is code backed, not aspirational.

## Claim 6: CARV is a gas token

CLAIM. From the token utility docs: "Gas Token, used to pay for the network computing costs of nodes in the blockchain." Aggregate marketing lists the token as paying gas and funding compute.

REALITY. OVERSTATED. No blockchain that CARV operates on today charges gas in CARV. The live verifier protocol runs on Arbitrum, where gas is ETH, and CARV goes further out of its way to remove even that cost from operators by relaying their transactions through a centralized gasless service. The CARV SVM chain, where CARV could plausibly be the gas token, is testnet only and its testnet gas token is Sepolia ETH, not CARV (see Claim 7). "Gas token" is therefore a roadmap property of an unshipped mainnet, not a present fact.

EVIDENCE.
- `verifier/configs/config.yaml`: `chain_id: 42161` (Arbitrum, ETH gas) and `gasless_service.url: https://protocol-api.carv.io`.
- docs.carv.io svm chain bridge material: testnet deposits are denominated in "Sepolia ETH."

IMPACT. Medium. The gas utility is presented in the present tense but is not realized on any live network.

## Claim 7: the CARV SVM chain

CLAIM. CARV markets a "CARV SVM Chain," described as "an AI agentic infrastructure that extends SVM's capabilities onto Ethereum" that "combines Solana's scalability with Ethereum's security."

REALITY. FALSE as a shipped mainnet, real as a testnet. The documentation itself places the SVM chain at testnet with mainnet "Coming soon," and its testnet native gas token is Sepolia ETH. There is no SVM chain node, runtime, or rollup implementation in the carv-protocol organization; the only Solana artifact under CARV is `solana-oft-example`, a LayerZero OFT deployment example, not a chain. Presenting the SVM chain as a live flagship product overstates a testnet.

EVIDENCE.
- docs.carv.io svm-ai-agentic-chain material: testnet only, mainnet "Coming soon," bridge gas denominated in Sepolia ETH.
- No SVM chain source in any carv-protocol repository; keyword search for svm and Solana virtual machine returns only third party upstreams that were excluded, plus the `solana-oft-example` deployment scripts.

IMPACT. High for anyone valuing CARV on the premise that the SVM chain is generating mainnet activity today. It is a testnet, and the live protocol economy (verifier nodes) currently runs on Arbitrum instead.

## Claim 8 and 9: the D.A.T.A. framework

CLAIM. D.A.T.A. is the "Data Authentication, Trust, and Attestation framework," an AI native system giving agents "seamless access to high-quality on chain and off chain data."

REALITY. CONFIRMED IN CODE that the framework exists and is open source, OVERSTATED on what its name implies. The `d.a.t.a` repository is a real Go project: an AI agent framework and Eliza plugin that fetches blockchain and social data and reasons over it with LLMs (DeepSeek and OpenAI). What it is not is an authentication or attestation system. The actual blockchain data is retrieved by calling CARV's centralized REST API (`https://api.carv.io/v1`) with an API key in the Authorization header. So the framework is a client for a proprietary data service plus an LLM agent loop; the "Authentication, Trust, and Attestation" in the acronym describes an aspiration, and the real attestation machinery lives in the separate `verifier` repository, not here.

EVIDENCE.
- `d.a.t.a/README.md`: "Built as a plugin for AI frameworks like Eliza," multichain data access, DeepSeek and OpenAI configuration.
- `d.a.t.a/src/pkg/carv/carv.go:34-59`: HTTP client that issues `GET` requests to the CARV API with `req.Header.Add("Authorization", d.APIKey)`; `d.a.t.a/src/config/config.yaml:25` `url: "https://api.carv.io/v1"` and `:18` DeepSeek base URL.
- `d.a.t.a/src/plugins/plugin-d.a.t.a/actions/fetch_transaction.go` and `providers/database_provider.go` implement data fetch, not cryptographic attestation.

IMPACT. Low. The framework is genuinely open source and usable, but its data layer value depends on CARV's centralized API, and the "attestation" framing oversells a data fetch and LLM agent.

## Claim 10: where the verifier network actually runs

CLAIM. Marketing associates the verifier network with the CARV SVM chain and cites a large node count.

REALITY. OVERSTATED. The shipped verifier binary is configured against Arbitrum (`chain_id: 42161`), and its ProtocolService and reward flow are Arbitrum contracts, not SVM chain programs. The docs' node count figures could not be independently verified from a single RPC read and are treated as unverified marketing. The infrastructure is real and deployed; the chain it is attributed to in marketing is not the chain it runs on in the config.

EVIDENCE.
- `verifier/configs/config.yaml`: Arbitrum chain id and Arbitrum ProtocolService address `0xa91fF8b606BA57D8c6638Dd8CF3FC7eB15a9c634`.

IMPACT. Low. This is an attribution mismatch rather than a missing capability.

## Positive Findings

1. The ERC20 is a clean, standard LayerZero OFT V2 with no owner `mint`, no pause, and multisig style contract ownership. It is not a honeypot and not inflatable by an admin.
2. TEE attestation is really implemented. The Intel SGX DCAP quote verifier in `verifier/pkg/dcap` is substantial, real code (quote parsing, ECDSA, PCK certificate chain, TCB and enclave identity), not a stub.
3. The on chain verifier economy is fully coded and deployed on Arbitrum: registration, VRF based verifier selection, majority settlement, slashing, and CARV rewards from a Vault.
4. CARV has genuine present day utility: veCARV vote escrow staking, verifier node license purchase priced in CARV, node reward payout in CARV, and governance via CarvGovernor and CarvVotes.
5. Deployment scripts exist for every advertised OFT chain, and the docs are unusually candid in places (for example openly stating the SVM chain mainnet is "Coming soon").

## Conclusion

CARV is a real project with a clean token and a meaningful amount of shipped infrastructure, wrapped in marketing that describes a more finished and more trustless system than the code delivers. Verdict: PASSED at 74 out of 100, MEDIUM RISK. The token risk on its own is low. The medium rating reflects the distance between claim and code: the flagship "zk plus TEE" attestation is only TEE in the source, the "gas token" utility is not realized on any live network, and the "CARV SVM Chain" is a testnet presented with mainnet weight. What is real is genuinely real, an SGX DCAP verifier, an Arbitrum verifier economy, vote escrow staking, and CARV native node licensing, and it is code backed with file and line evidence. What is oversold is oversold in the familiar direction of crypto roadmaps: forward looking capabilities described in the present tense. Buyers should value CARV on its live Arbitrum verifier network and token utility, and discount the SVM chain and ZK narratives until mainnet and zkVM code actually ship.
