## Why This Report Exists

Most reports we publish document projects whose code contradicts their marketing. Fluence is the other kind of subject: a compute project with real engineering shipped over years. The discipline is the same. We read the actual code, claim by claim, credit what is genuinely implemented, and flag where the marketing runs ahead of the source or where centralization sits under a trustless narrative.

We are not making accusations and we are not spreading FUD. Fluence earns real credit on this pass. The Proof of Capacity engine is genuinely in the deployed contract interface, RandomX proving genuinely runs on the provider machine, staking collateral and slashing are real on chain primitives, the marketplace matches deals to independent providers on chain, Aqua and AquaVM are substantive real software, and the FLT token is exactly the UUPS upgradeable proxy under a two of four Gnosis Safe that the on chain data shows. The caveats that remain are honest ones about custody of upgrade power and about supporting infrastructure that Fluence Labs operates.

## Method

For every major claim we located the relevant code. The Rust peer node (nox), the RandomX capacity prover (capacity-commitment-prover), and the Aqua execution stack (aquavm) are public and were read from source. The on chain marketplace and capacity contracts (the former `fluencelabs/deal` repository) are no longer served as a public source repository (see The Foundation), so for those we read the authoritative contract interface Fluence itself publishes as the npm package `@fluencelabs/deal-ts-clients@0.3.0` (TypeChain types generated from the real ABIs) together with its committed deployment address book, and we verified the live deployed state directly against Ethereum mainnet by JSON-RPC (`eth_call`, `eth_getStorageAt`). Each claim below is labelled CONFIRMED IN CODE, OVERSTATED, or FALSE, with a file path, function or storage slot, and the value read.

## The Foundation: The Contract Source Repository Is No Longer Public

**CLAIM:**
> Fluence is open source; the marketplace and capacity contracts live at github.com/fluencelabs/deal.

**REALITY:** OVERSTATED. The peer node, the RandomX prover, and AquaVM are all public and return HTTP 200. The Solidity source repository that holds the marketplace, deal, and Proof of Capacity contracts is not reachable. `github.com/fluencelabs/deal`, its `raw.githubusercontent.com` README on both `main` and `master`, and its `codeload` archive all return HTTP 404, while sibling repositories download normally. The chain (chainId 9999999) is not indexed by Sourcify and its Blockscout instance sits behind Cloudflare, so no third party verified copy of the contract source is retrievable either.

**EVIDENCE:**
```
GET github.com/fluencelabs/deal                              -> 404
GET raw.githubusercontent.com/fluencelabs/deal/main/README   -> 404
GET raw.githubusercontent.com/fluencelabs/deal/master/README -> 404
GET codeload.github.com/fluencelabs/deal/tar.gz/refs/...     -> 404
GET github.com/fluencelabs/aquavm                            -> 200
GET github.com/fluencelabs/nox                               -> 200
GET github.com/fluencelabs/capacity-commitment-prover        -> 200
Sourcify /files/any/9999999/<CapacityImpl>  -> "Chain 9999999 is not a Sourcify chain!"
```
The only surviving public artifact of the contract code is the compiled interface shipped by Fluence to npm: `@fluencelabs/deal-ts-clients@0.3.0` (82 published versions), which contains the full ABIs as TypeChain types plus `src/deployments/kras.json` with every deployed address.

**IMPACT:** The economic and security logic that this report evaluates (Proof of Capacity, staking, slashing, matching) is real and its interface is verifiable, but a reader cannot currently audit the Solidity implementation line by line from a public repository, and the deployed bytecode is not independently source verified. That is a transparency regression against the "open source" framing and against a peer such as iExec whose contracts are public and carry committed audit reports. Informational to Low, and the reason this otherwise strong project is not scored higher.

## Claim 1: A decentralized cloudless compute marketplace running on independent providers

**CLAIM:**
> "Slash your cloud bill by up to 85%." A decentralized, cloudless compute marketplace where independent providers supply the servers, not a central operator.

**REALITY:** CONFIRMED IN CODE. The marketplace is a genuine on chain market. A provider registers an offer with its own compute peers and compute units, sets a price per worker epoch, and lists effectors and hardware; a customer deploys a deal that names an application CID and a target worker count; matching happens on chain, and providers' compute units join the deal as workers and are paid per epoch. The actual compute runs on the provider operated `nox` peer, which the project describes as the Host for all Workers, distributed as a plain Docker image that anyone can run.

**EVIDENCE:**

**IMPACT:** Positive. This is a real decentralized marketplace: offers, peers, compute units, deals, matching, per epoch payment, and worker assignment are all on chain, and the workloads execute on provider owned hardware rather than in a Fluence data center. The honest caveats are the supporting infrastructure Fluence Labs operates (a hosted Console at fluence.dev, relay peers, and the deal indexer subgraph at graph-node.fluence.dev that the client uses to find matchable units before the on chain `matchDeal`). Informational.

## Claim 2: Proof of Capacity secures the network

**CLAIM:**
> The network is secured by Proof of Capacity. Providers continuously prove that committed CPU capacity is really allocated to Fluence, validated on the Fluence chain.

**REALITY:** CONFIRMED IN CODE. Proof of Capacity is a real, deployed mechanism, not a slogan. The Capacity contract exposes the full lifecycle: create a commitment, deposit collateral, submit RandomX proofs per compute unit against an epoch difficulty and a global nonce, accrue rewards, and finish the commitment. The proving work itself is done off chain on the provider machine by the open source `capacity-commitment-prover`, which is a substantial Rust project built around RandomX (the same CPU hard hashing used by Monero), and a `RandomXProxy` contract is deployed on chain to validate proofs.

**EVIDENCE:**
```

createCommitment, depositCollateral, submitProof, commitSnapshot,
getGlobalNonce, finishCommitment, removeCUFromCC, withdrawReward, randomXProxy
// events: CommitmentCreated, CommitmentActivated, ProofSubmitted,
//         UnitActivated, UnitDeactivated, CommitmentFinished

submitProof(bytes unitId, bytes globalUnitNonce, bytes localUnitNonce, bytes targetHash)
```
```
// src/deployments/kras.json  (Fluence mainnet, chainId 9999999)
"Capacity":     { "addr": "0xCCAFAddc84210b06dC6c89E6cA41d53d497d0801" }
"CapacityImpl": { "addr": "0xc81777E28b805Ec7C9f7f5D9892417F548d1782f" }
"RandomXProxy": { "addr": "0x965Df0814124d678109404A01fFD0F13239EfBEf" }
```
```

 unit was really allocated to the Fluence network during some epoch.

```

**IMPACT:** Positive. The Proof of Capacity design is present end to end: an on chain contract that issues commitments and verifies proofs against difficulty and a rotating global nonce, and a real provider side prover that keeps CPUs busy computing RandomX. This is the load bearing security claim and it holds. Informational.

## Claim 3: Providers stake FLT (about 200 per core) with slashing

**CLAIM:**
> Providers stake FLT collateral, about 200 per core, and are slashed for failing to prove capacity. Documentation states 200 USD of stake per core (about 12,000 for a 64 core server with 60 active cores) and slashing of 0.3 percent per epoch up to a 1.5 percent maximum.

**REALITY:** CONFIRMED IN CODE, with one precision correction. Staking and slashing are genuinely implemented: collateral is deposited per compute unit into the Capacity contract, and a slashing rate plus a failed ratio threshold and a withdraw delay govern the penalty for missing proofs. The precision correction is that the collateral is denominated in USD, not in a flat 200 FLT. The contract stores `usdCollateralPerUnit` and converts it to an FLT amount through `fltPrice`, so "200 per core" is 200 USD of FLT at the price the protocol sets, not 200 tokens.

**EVIDENCE:**
```
// deal-ts-clients@0.3.0 src/typechain-types/ICapacityConst.ts (function union)
usdCollateralPerUnit  (view)      // collateral per compute unit, USD denominated
fltCollateralPerUnit  (view)      // the FLT amount after conversion
fltPrice              (view)      // FLT/USD price used for the conversion
setFLTPrice           (nonpayable)// price is *set*, not read from a market oracle
slashingRate          (view)      // the slash percentage
maxFailedRatio, withdrawEpochesAfterFailed, minRequierdProofsPerEpoch,
maxProofsPerEpoch     (view)      // failure and proof-rate thresholds
// event FLTPriceUpdated
```
```
// src/typechain-types/ICapacity.ts
depositCollateral(...)            // provider stakes FLT collateral
// collateral is returned via finishCommitment / removeCUFromCC
```
Fluence's own staking documentation states the collateral as "200 in stake per core", a 60 active core server needing "12,000 in FLT", and slashing "by 0.3% every next epoch until it reaches the maximum of 1.5%". The contract fields (`usdCollateralPerUnit`, `slashingRate`, `maxFailedRatio`) are exactly the knobs that implement those figures.

**IMPACT:** Positive on substance. Staking (`depositCollateral`) and slashing (`slashingRate`, `maxFailedRatio`, `withdrawEpochesAfterFailed`) are real on chain economics tied to Proof of Capacity performance. The caveat is that the collateral requirement is USD pegged and the FLT price is set through `setFLTPrice` by the contract owner rather than read from a decentralized oracle, so the effective FLT amount a provider must lock is an owner tunable parameter. "About 200 per core" should be read as "about 200 USD of FLT at an owner set price," not a fixed token count. Low.

## Claim 4: CPU and GPU compute

**CLAIM:**
> The network provides both CPU and GPU compute.

**REALITY:** OVERSTATED as an in code claim. Everything that is secured and metered by the protocol is CPU. The unit of account is the CPU core: capacity is measured in compute units, collateral is priced per unit, and the proof of capacity is RandomX, which is a CPU algorithm (the prover README and crates are entirely CPU and RandomX, with model specific register tuning for CPUs, and no GPU code). GPU is a property of a rentable server offered at the marketplace layer (a provider can list hardware and effectors on an offer), not something the Proof of Capacity or the on chain accounting models. We found no GPU specific logic in the public capacity prover or in the deployed contract interface.

**EVIDENCE:**
```
// capacity-commitment-prover  crates/: randomx, cu-worker, cpu-utils, msr
//   (msr = CPU model-specific registers; no GPU/CUDA/OpenCL crate)
// ICapacityConst.ts: activeUnitCount, usdCollateralPerUnit  -> per CPU compute unit
// IMarket.ts: addEffector / getEffectorInfo / setProviderInfo -> free-form
//   hardware & capability listing, where GPU servers would be advertised
```

**IMPACT:** GPU compute is a genuine hardware offering a provider can rent out through a deal, so it is not a fabrication, but it is not part of the protocol's Proof of Capacity or its staking and slashing security. The accurate statement is "CPU compute secured by CPU based Proof of Capacity, plus GPU capable servers rentable through the marketplace." Medium as a marketing versus code gap.

## Claim 5: Aqua and AquaVM exist as claimed

**CLAIM:**
> Fluence composes distributed services with the Aqua language, executed by AquaVM over AIR (Aqua Intermediate Representation).

**REALITY:** CONFIRMED IN CODE. AquaVM is a real, substantial, independently published piece of software. ## Claim 6: FLT is a UUPS upgradeable proxy under a two of four Gnosis Safe

**CLAIM:**
> The FLT token at 0x236501327e701692a281934230AF0b6BE8Df3353 is a UUPS upgradeable proxy governed by a two of four Gnosis Safe.

**REALITY:** CONFIRMED IN CODE, verified live against Ethereum mainnet. The token is an ERC1967 proxy whose implementation slot is populated and whose admin slot is empty (the signature of a UUPS proxy, where upgrade authorization lives in the implementation, not in a separate ProxyAdmin). The implementation answers `proxiableUUID()` with exactly the EIP-1967 implementation slot (the ERC1822 UUPS marker), and the same call through the proxy reverts with the OpenZeppelin `notDelegated` guard, which is textbook OpenZeppelin `UUPSUpgradeable`. The proxy `owner()`, the address UUPS `_authorizeUpgrade` gates on, is a Gnosis Safe version 1.3.0 with threshold two and four owners.

**EVIDENCE:**
```
// Ethereum mainnet, token 0x2365...3353
name()        = "Fluence"      symbol() = "FLT"
totalSupply() = 0x033b2e3c9fd0803ce8000000 = 1,000,000,000e18

eth_getStorageAt(token, 0x360894...382bbc /*EIP-1967 impl*/ )
   = 0x...bdb50eff425fb2b1b67fea21b8420eeb6d99ccc0     // implementation set -> proxy
eth_getStorageAt(token, 0xb53127...5d6103 /*EIP-1967 admin*/ )
   = 0x0                                               // empty -> UUPS, not Transparent
proxiableUUID() on impl 0xbdb5...ccc0
   = 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc  // ERC1822/UUPS
proxiableUUID() via proxy -> revert 0xe07c8dba          // OZ notDelegated guard

owner() = 0x7f629403fdcc02ad83aa5debd1d4b1548982afac
```
```
// the owner is a Gnosis Safe (verified on mainnet)
getThreshold() = 2
getOwners()    = [ 0xbe8c3dd6ecadeeccfecc447bedc3c15f78b1e8b0,
                   0x179819e82030e4ca30c9595f7fddb4c73d6eeac7,
                   0x6d3ef640e16eb582a3bf625b1789e837e020c797,
                   0x11e41ee1566834acb84bd37cedf66bfc370c7106 ]   // 4 owners
VERSION()      = "1.3.0"
slot0 masterCopy = 0xd9db270c1b5e3bd161e8c8503c55ceabee709552     // canonical Safe 1.3.0 singleton
```

**IMPACT:** The claim is exactly true: a UUPS proxy governed by a two of four Safe. The honest consequence for holders is that this is a mutable token: any two of the four signers can push a new implementation through `upgradeToAndCall` and change transfer logic, minting, or the "fixed" one billion supply. That is standard, reasonably governed multisig control rather than a single key, but it is not immutable and it is not trustless. Two signatures can rewrite the token. High, as the single largest trust dependency for holders.

## Claim 7: Trustless, permissionless protocol economics

**CLAIM:**
> The protocol is trustless and enforced by smart contracts; providers and stakers rely on code, not an operator.

**REALITY:** OVERSTATED. The enforcement is real (Claims 1 to 3), but several economically decisive parameters are owner controlled rather than market or governance driven, and the deployed contracts are upgradeable. The Capacity and Core contracts expose owner only setters for the collateral price, the proof difficulty, and general constants, and the deal system contracts are deployed behind upgradeable proxies with separate implementation addresses (the Capacity, Core, and Market proxies share one proxy bytecode, each delegating to its own Impl), carrying both a `UUPSUpgradeable` surface and an `OwnableUpgradableDiamond` owner.

**EVIDENCE:**
```
// ICapacityConst.ts / ICapacity.ts  (owner-tunable economics)
setFLTPrice(...)     // sets FLT/USD used for collateral (Claim 3)
setDifficulty(...)   // sets Proof of Capacity difficulty
setConstant(...)     // sets protocol constants (also in ICore.ts)
// ICore.ts: capacity, market, fluenceToken, epochDuration, setConstant

// kras.json: proxy + separate Impl for every module -> upgradeable
Capacity 0xCCAF... / CapacityImpl 0xc817...
Core     0xF1A0... / CoreImpl     0x4598...
Market   0xab29... / MarketImpl   0x6988...
Deal(Impl) 0xD1E9...
// UUPSUpgradeable.ts: upgradeTo, upgradeToAndCall, proxiableUUID
// OwnableUpgradableDiamond.ts: owner, transferOwnership
```

**IMPACT:** The provider economics depend on an owner set FLT price and difficulty, and the whole marketplace and capacity logic can be upgraded by the contracts' owner on the Fluence chain. This is normal for an evolving protocol and is not evidence of bad faith, but "trustless" overstates it: the accurate description is a working, enforced economic protocol whose price, difficulty, and code are under the control of Fluence governance. Medium.

## Additional Note: Supporting infrastructure is operator run

Worth stating plainly because it qualifies the "decentralized" claim without contradicting it. Compute executes on independent provider hardware and matching settles on chain, but Fluence Labs operates the convenience and coordination layer around it: the hosted Console at fluence.dev, relay peers that clients dial into, and the deal indexer subgraph at graph-node.fluence.dev that the official client queries to discover matchable compute units before submitting the on chain `matchDeal`. None of these custody user funds, and a determined participant can run a peer and match deals without them, but in practice most activity flows through Fluence operated infrastructure. Low, design disclosure.

## Conclusion

Fluence is a genuine decentralized compute project whose code substantially delivers what it markets, and it earns a high score for it. Proof of Capacity is a real deployed mechanism with on chain commitments, RandomX proofs, and a live provider side prover (Claim 2). Staking and slashing are real on chain economics tied to proving performance (Claim 3). The marketplace matches deals to independent providers on chain and the work runs on provider operated nox peers (Claim 1). Aqua and AquaVM are substantive real software (Claim 5). The FLT token is exactly the UUPS proxy under a two of four Gnosis Safe that is claimed, verified live on Ethereum mainnet (Claim 6). No claim in this review is fabricated, and there are no hidden bypasses of the kind that sink weaker projects.

The deductions are honest ones about custody of power and about transparency. The token is upgradeable by two of four signers, so it is mutable rather than immutable (Claim 6). The protocol economics lean on an owner set FLT price and difficulty and on upgradeable contracts, so "trustless" is overstated (Claim 7). GPU is a rentable hardware offering, not part of the CPU based Proof of Capacity that actually secures the network (Claim 4). "200 per core" is 200 USD of FLT at an owner set price, not 200 tokens (Claim 3). And most notably, the marketplace and capacity Solidity source is no longer served from a public repository, so the implementation cannot currently be audited line by line and the deployed bytecode is not source verified (The Foundation), which is the specific reason this project scores 80 rather than higher. Score 80 out of 100, LOW to MEDIUM RISK, driven by upgrade custody and transparency caveats rather than by any dishonest or broken code.
