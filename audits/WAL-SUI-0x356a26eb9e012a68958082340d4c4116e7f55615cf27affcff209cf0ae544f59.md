## Why This Report Exists

Walrus is marketed as a decentralized storage and data availability network built by Mysten Labs on Sui, using an erasure coding scheme called Red Stuff, with on chain proof of storage, challenge and slashing, a staked committee of storage nodes, and a WAL token for payment and staking. Those are strong claims. This report reads the actual public Rust and Move source, traces each flagship claim to concrete files and lines, and checks the live token and protocol objects on Sui mainnet. The goal is to separate genuine engineering from marketing language. No team or personnel analysis is included. The token contract is covered but treated as secondary to the whole product.

## Method

1. Cloned github.com/MystenLabs/walrus at commit `248a771` and read the Move contracts under `contracts/` and the Rust crates under `crates/`, with primary focus on `walrus-core` (encoding), the `walrus` Move package (system, staking, slashing, upgrade), and the `wal` Move package (token).
2. Confirmed the live token independently on Sui mainnet. Public JSON RPC is deprecated, so a GraphQL endpoint was used to read coin metadata, total supply, and object ownership. Package immutability was checked via object owner type.
3. For every major claim, an explicit verdict of CONFIRMED IN CODE, OVERSTATED, or FALSE is assigned with a repo path, file, line, and a verbatim snippet.
4. Design claims were taken from the repo's own design docs under `docs/content/system-overview/` and the README, which stand in for the whitepaper, then tested against code.

## The Foundation: What Walrus Actually Is

Walrus is a real, substantial codebase, not a shell. The `walrus` Move package implements a full storage marketplace and a staked committee governed through Sui: blob registration and certification, storage space reservation and accounting, delegated staking with per epoch committee selection and shard assignment, price voting, slashing, and quorum based contract upgrades. The `walrus-core` Rust crate implements the two dimensional Red Stuff erasure code over a Reed Solomon backend. The system is live on mainnet with 1000 shards, and the on chain system object has already been upgraded through internal version 3, which is consistent with an actively operated network rather than a static deployment.

The single most important structural fact is the split of mutability. The WAL token package is immutable and its treasury is neutered, so the token is genuinely fixed supply. The storage protocol package, by contrast, is upgradeable, both through a storage node quorum vote and through an emergency capability held outside that quorum. The token is locked down; the protocol logic is not. That distinction drives most of the findings below.

## Claim 1: Genuine erasure coded storage with Red Stuff

CLAIM. The design docs state: "erasure coding allows you to recover a blob even if $N - k$ storage nodes fail, providing high availability and durability" and describe Red Stuff as a two dimensional scheme with primary and secondary slivers and a storage overhead constant of about 4.5 (`docs/content/system-overview/red-stuff.mdx`).

REALITY: CONFIRMED IN CODE. Red Stuff is a real two dimensional erasure code. Both the Rust encoder and the on chain length accounting implement primary and secondary source symbols derived from Byzantine fault tolerance parameters, where the maximum number of faulty shards is `(n_shards - 1) / 3`.

EVIDENCE.
```move
// contracts/walrus/sources/system/redstuff.move:27-35
/// The number of primary source symbols per sliver given `n_shards`.
fun source_symbols_primary(n_shards: u16): u16 {
    n_shards - 2 * max_byzantine(n_shards)
}
/// The number of secondary source symbols per sliver given `n_shards`.
fun source_symbols_secondary(n_shards: u16): u16 {
    n_shards - max_byzantine(n_shards)
}
```
```move
// contracts/walrus/sources/system/redstuff.move:64-67
fun max_byzantine(n_shards: u16): u16 {
    (n_shards - 1) / 3
}
```
The Rust side encodes real symbols through a hardware accelerated Reed Solomon library:
```rust
// crates/walrus-core/src/encoding/basic_encoding.rs:128-133
let encoder = reed_solomon_simd::ReedSolomonEncoder::new(
    Self::reed_solomon_original_count(n_source_symbols),
    Self::reed_solomon_recovery_count(n_source_symbols, n_shards),
    Self::reed_solomon_shard_bytes(symbol_size),
)
```

IMPACT. The core storage primitive is genuine. This is not replication dressed up as erasure coding. The two dimensional layout is what enables cheap single node recovery, which is the whole point of Red Stuff.

## Claim 2: RaptorQ fountain code encoding

CLAIM. The public design doc is titled and keyworded around RaptorQ: "Learn how the RedStuff encoding algorithm works in Walrus, including erasure coding, RaptorQ fountain codes" and the worked example states "Thanks to the linearity of RaptorQ" (`docs/content/system-overview/red-stuff.mdx`, `docs/content/system-overview/red-stuff-details.mdx`). Many third party writeups repeat "RaptorQ style encoding."

REALITY: OVERSTATED. The RaptorQ variant exists in the type system only as a deprecated, unsupported historical option. Mainnet uses Reed Solomon (`RS2`), and RaptorQ is explicitly rejected at deserialization. The documentation still describes RaptorQ, which is a live site versus code mismatch.

EVIDENCE.
```rust
// crates/walrus-core/src/lib.rs:768-784

    /// Original RedStuff encoding using the RaptorQ erasure code (no longer supported).
    RedStuffRaptorQ,
    /// RedStuff using the Reed-Solomon erasure code.
    RS2,
}
...
pub enum EncodingType {
    /// RedStuff using the Reed-Solomon erasure code.
    RS2 = 1,
}
```
```rust
// crates/walrus-core/src/lib.rs:792-795
match value {
    EncodingTypeForSerde::RedStuffRaptorQ => Err(InvalidEncodingType),
    EncodingTypeForSerde::RS2 => Ok(EncodingType::RS2),
}
```
The only supported and default encoding is Reed Solomon, confirmed by the single dependency `reed-solomon-simd` and the constant:
```rust
// crates/walrus-core/src/lib.rs:87-88
const SUPPORTED_AND_DEFAULT_ENCODING: (&[EncodingType], EncodingType) =
    (&[EncodingType::RS2], EncodingType::RS2);
```

IMPACT. Low technical impact, since Reed Solomon is a sound and arguably stronger choice than RaptorQ for this workload, but it is a real accuracy problem: the flagship docs advertise a codec the production code no longer supports. Anyone integrating against the "RaptorQ" description would be working from stale information.

## Claim 3: On chain proof of storage

CLAIM. Marketing describes "on chain proof of storage." The verify docs frame the guarantee as certification: a blob "moves through two states: registered ... and certified, where enough slivers are stored to guarantee availability" (`docs/content/walrus-client/verifying-availability.mdx`).

REALITY: OVERSTATED as literally worded, CONFIRMED as certified availability. There is no continuous cryptographic proof of storage over time in the Filecoin proof of spacetime sense. Instead, storage nodes that hold slivers issue signed storage confirmations, and a Byzantine quorum of those confirmations, aggregated as one BLS signature, is verified on chain to move a blob to certified. Ongoing storage is checked economically through light peer audits that adjust rewards, not through a periodic cryptographic challenge of every blob.

EVIDENCE.
```move
// contracts/walrus/sources/system/system_state_inner.move:351-368
public(package) fun certify_blob(
    self: &SystemStateInnerV1,
    blob: &mut Blob,
    signature: vector<u8>,
    signers_bitmap: vector<u8>,
    message: vector<u8>,
) {
    let certified_msg = self
        .committee()
        .verify_quorum_in_epoch(signature, signers_bitmap, message);
    assert!(certified_msg.cert_epoch() == self.epoch(), EInvalidIdEpoch);
    let certified_blob_msg = certified_msg.certify_blob_message();
    blob.certify_with_certified_msg(self.epoch(), certified_blob_msg);
}
```
The quorum threshold is the classic 2f+1 by shard weight:
```move
// contracts/walrus/sources/system/bls_aggregate.move:163-166
public(package) fun is_quorum(self: &BlsCommittee, weight: u16): bool {
    3 * (weight as u64) >= 2 * (self.n_shards as u64) + 1
}
```
Continuing storage is priced from measured performance and audits, not a cryptographic proof: "the fund distributes WAL to storage nodes based on their measured performance, which is determined through light audits of each other" (`docs/content/system-overview/wal-tokenomics-faq.mdx`).

IMPACT. Medium. The on chain certification of availability at a point in time is real and quorum backed, which is what actually matters for a consumer of a blob ID. But the phrase "proof of storage" implies continuous cryptographic proof that does not exist here. Integrators should rely on the certified `Blob` object and its `end_epoch`, and understand that durability past certification is enforced by incentives and audits rather than by a per blob storage proof.

## Claim 4: On chain challenge and slashing via Move contracts

CLAIM. Walrus advertises challenge and slashing of misbehaving storage nodes enforced on chain.

REALITY: CONFIRMED IN CODE, with an important scope nuance. Two distinct mechanisms exist. First, an inconsistency challenge: any single honest node can prove a blob was encoded inconsistently, and the chain marks the blob ID invalid. Second, committee voting to slash a node. The nuance, which the docs state honestly, is that slashing burns the node operator's accumulated commission, never the delegated principal.

EVIDENCE. The challenge path requires proof from at least one correct node (the f+1 threshold), then emits an invalid blob event:
```move
// contracts/walrus/sources/system/system_state_inner.move:292-314
public(package) fun invalidate_blob_id(
    self: &SystemStateInnerV1,
    signature: vector<u8>,
    members_bitmap: vector<u8>,
    message: vector<u8>,
): u256 {
    let certified_message = self
        .committee
        .verify_one_correct_node_in_epoch(signature, members_bitmap, message);
    ...
    events::emit_invalid_blob_id(epoch, blob_id);
    blob_id
}
```
Slashing is a quorum vote that burns commission only:
```move
// contracts/walrus/sources/slashing.move:95-110
public fun execute_slashing(
    self: &mut SlashingManager,
    staking: &mut Staking,
    treasury: &mut ProtectedTreasury,
    candidate_node_id: ID,
    ctx: &mut TxContext,
) {
    assert!(self.slashing_candidates.contains(candidate_node_id), ENoProposalForNode);
    let proposal = self.slashing_candidates.remove(candidate_node_id);
    assert!(proposal.epoch == staking.epoch(), EWrongEpoch);
    assert!(staking.is_quorum(proposal.voting_weight), ENotEnoughVotes);
    // Burn the commission from the slashed node's staking pool.
    staking.burn_commission(candidate_node_id, treasury, ctx);
}
```
The docs match the code exactly: "Walrus never slashes your delegated principal ... executing that slash burns the node operator's accumulated commission, not the WAL you delegated" (`docs/content/system-overview/wal-tokenomics-faq.mdx`).

IMPACT. Positive that both enforcement paths are on chain and quorum gated. A delegator should understand that slashing does not put their principal at risk, so slashing is a mild deterrent on operators rather than a hard economic penalty on stake. Delegator downside is limited to reduced rewards from poor node performance.

## Claim 5: Storage node staking, committee and epoch model

CLAIM. Walrus runs delegated proof of stake, with a committee of storage nodes selected each epoch and shards assigned in proportion to stake.

REALITY: CONFIRMED IN CODE. Node registration and delegation are permissionless. The committee is stake weighted, refreshed per epoch, and shards are distributed across nodes, with a cap on how many shards any one node may hold.

EVIDENCE. The public staking API includes open registration, delegation, committee computation, and epoch change:
```move
// contracts/walrus/sources/staking.move (public entry surface)
79:  public fun register_candidate(...)
184: public fun compute_next_committee(staking: &Staking): Committee
268: public fun initiate_epoch_change(staking: &mut Staking, system: &mut System, clock: &Clock)
315: public fun stake_with_pool(...)
329: public fun request_withdraw_stake(...)
```
Shards are concentration limited and the active node set is capped:
```move
// contracts/walrus/sources/staking/staking_inner.move:38-47
/// Temporary upper limit for the number of storage nodes.
const TEMP_ACTIVE_SET_SIZE_LIMIT: u16 = 150;
const MIN_NODES_FOR_SHARDS_LIMIT: u8 = 20;
/// The maximum number of shards per node as a denominator of the total number of shards.
const SHARDS_LIMIT_DENOMINATOR: u8 = 10; // 10%
```
Mainnet parameters confirm a live epoch model: 1000 shards and a 2 week epoch duration (`docs/content/network-reference.mdx`), and the live system object internal version is 3, consistent with a running network.

IMPACT. The economic security model is real and open to participation. The 150 node cap is described in code as temporary, and it is the main practical limit on how decentralized the committee can be today. Verdict is a genuine delegated proof of stake system with a modest committee size.

## Claim 6: Blob availability guarantee

CLAIM. Walrus guarantees blob availability and durability once data is stored.

REALITY: CONFIRMED IN CODE, time bounded. Availability is guaranteed for a certified blob until its purchased storage period ends, not perpetually. The chain records a `certified_epoch` and an `end_epoch`, and both erasure coding redundancy (tolerating up to f faulty shards) and the certified quorum back the guarantee within that window.

EVIDENCE. The verify docs and the on chain `Blob` fields make the bounded window explicit: "A blob is safe to depend on only after it is certified, and only until its storage period ends" and a certified example shows `certifiedEpoch: 34`, `endEpoch: 35`, `deletable: false` (`docs/content/walrus-client/verifying-availability.mdx`). Storage can be purchased for at most 53 epochs at a time (`docs/content/network-reference.mdx`), and blobs can be extended before expiry via `extend_blob` in `contracts/walrus/sources/system.move:204`.

IMPACT. The guarantee is honest but conditional. Consumers must read Sui state to confirm a blob is certified and unexpired before depending on it. A write acknowledgement or an aggregator HTTP 200 is explicitly not a durability guarantee, which the docs correctly warn about.

## Claim 7: WAL fixed supply, no inflation, deflationary burn

CLAIM. WAL has a fixed total supply of 5,000,000,000, is used for storage payment and staking, and has a deflationary burn.

REALITY: CONFIRMED IN CODE and on chain. Supply is minted once at genesis, the treasury cap is wrapped and no mint function is exposed, and the WAL package is immutable on chain, so no upgrade can add a mint. A per epoch burn of 3 percent of rewards is enforced in code, and the live on chain supply already sits below the cap.

EVIDENCE. Genesis mint with no residual mint path:
```move
// contracts/wal/sources/wal.move:10-11, 47-63

const DECIMALS: u8 = 9;
...

let minted_coin = cap.mint(total_supply_to_mint, ctx);

dof::add(&mut protected_treasury.id, TreasuryCapKey {}, cap);
transfer::share_object(protected_treasury);
```
Only `burn` is exposed on the treasury (`contracts/wal/sources/wal.move:71`), and a source comment states the intent that "the `UpgradeCap` must be burned to ensure that the supply of minted WAL cannot change" (`wal.move:33-34`). On chain verification confirms this was executed: the WAL package `0x356a26eb...` reports owner type `Immutable`, and live supply reads 4,999,942,717,678,061,104 FROST, below the 5,000,000,000,000,000,000 FROST genesis amount.
The 3 percent reward burn is real and matches the docs:
```move
// contracts/walrus/sources/system/storage_accounting.move:120-123
// Burn 3% of total rewards before distribution. This is roughly 25% of user payment when
...
let burn_amount = reward_balance.value() * 3 / 100;
reward_balance.split(burn_amount)
```
That burn is routed to the token burn at epoch change:
```move
// contracts/walrus/sources/staking.move:284-285

wal::wal::burn(treasury, burn_balance.into_coin(ctx));
```

IMPACT. Strong positive. The token is genuinely non inflationary and immutable, with an active deflationary sink. Third party claims of a "0.5 percent" burn are inaccurate; the code burns 3 percent of epoch rewards. The `staked_wal.move` mint at line 61 mints a staking receipt object, not WAL, so it does not affect supply.

## Claim 8: WAL utility and tradeability

CLAIM. WAL is used for storage payment, staking, and governance, and is a live tradeable asset.

REALITY: CONFIRMED IN CODE and in market. Storage and write fees are paid in WAL and routed into the storage fund (`register_blob` splits a WAL `write_payment_coin` in `system_state_inner.move:342-344`). Staking and price and upgrade governance are all WAL weighted, per the staking and upgrade modules. The token is live on Sui mainnet and trades on major venues (Binance spot, Coinbase, KuCoin, listed October 2025, quoted across dozens of exchanges).

IMPACT. Utility is not cosmetic. WAL is the settlement and security asset of a running network, and it is liquid.

## Positive Findings

1. The token is honestly fixed supply. Immutable package, wrapped treasury with no mint, only burn. This is the strongest single fact in the review and is verifiable on chain.
2. The core erasure code is real and well engineered. Two dimensional Red Stuff over a SIMD accelerated Reed Solomon backend, with Byzantine parameters wired consistently across the Rust encoder and the Move length accounting, kept in sync by explicit tests (`redstuff.move` test cases).
3. Enforcement is on chain and quorum gated. Blob certification (2f+1), the invalid blob challenge (f+1), slashing, and even contract upgrades all require aggregated committee signatures verified in Move, not a trusted server.
4. Documentation is unusually candid about limits. The docs openly state that principal is never slashed, that availability is bounded by the purchased storage period, and that a write acknowledgement is not a durability guarantee. Code matches these statements.
5. There is a real decentralization path for upgrades: storage nodes can pass a package upgrade by 2f+1 quorum vote (`upgrade.move`).

## Centralization Notes

- EmergencyUpgradeCap (Medium). Alongside the quorum upgrade path, an `EmergencyUpgradeCap` allows the holder, the Walrus Foundation or Mysten, to upgrade the storage protocol package without any node vote. The code itself flags this as temporary: "This should be used sparingly and once walrus has a healthy community and governance, the EmergencyUpgradeCap should be burned" (`contracts/walrus/sources/upgrade.move:156-171`). Until that cap is burned, the protocol logic (not the token) can be changed unilaterally. This could not be independently confirmed as burned and should be treated as an open trust assumption.
- Deny list (Low). The system supports deny listing blobs, with `register_deny_list_update`, `update_deny_list`, and `delete_deny_listed_blob` in `contracts/walrus/sources/system.move:387-418`. This is a content moderation and censorship surface, gated by node governance, and reduces rewards for denied capacity. It is a legitimate abuse control but is a centralization and censorship vector worth naming.
- Committee cap (Low). The active storage node set is capped at 150 by a constant described as temporary, with a per node shard cap of 10 percent. Committee decentralization is therefore bounded by policy today.

## Conclusion

Walrus is a genuine, technically substantive decentralized storage network, not a marketing shell. The flagship engineering claims check out against the real Rust and Move source: Red Stuff is a real two dimensional erasure code, blob availability is certified on chain by a 2f+1 BLS quorum, misbehavior is punished through an on chain invalid blob challenge and commission slashing, and the network runs a live delegated proof of stake committee with a per epoch model and 1000 shards on mainnet. The WAL token is the strongest element: fixed 5B supply, immutable package, no mint path, an active 3 percent reward burn, and genuine utility as the payment and staking asset, all confirmed on chain, where live supply already sits below the cap.

The deductions are accuracy and centralization, not fraud. The public docs still advertise RaptorQ while production runs Reed Solomon, and the phrase "proof of storage" overstates what is really a certified availability plus economic audit model. On centralization, the storage protocol package remains upgradeable through an emergency capability that bypasses the node quorum, a deny list can censor blobs, and the committee is capped at 150 nodes. None of these are hidden; the code and docs disclose them.

Weighing genuine, verifiable engineering and an honestly fixed and immutable token against upgradeability and a modest committee, Walrus clearly passes.
