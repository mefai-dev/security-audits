## Why This Report Exists

Most reports we publish document projects whose code contradicts their marketing. Streamr is the other kind of subject: a project that has shipped a working peer to peer network and on chain tokenomics continuously since its 2017 token sale. The discipline is the same regardless. We read the actual public source, claim by claim, credit what is genuinely implemented, and flag where the marketing runs ahead of the code.

We are not making accusations and we are not spreading FUD. We read the source and show what is actually implemented. Streamr earns real credit on this pass. The peer to peer network is real code, not a diagram. The on chain Operator staking, delegation, Sponsorship, and slashing are real and substantive. Stream creation and Operator deployment are genuinely permissionless. The single caveat that a token holder must understand is that the DATA supply is not fixed. The token is mintable with no cap in the contract, and the mint authority sits with a 2 of 6 Gnosis Safe multisig, which we verified on chain.

## Method

For every major marketing or documentation claim we located the relevant code in the real repositories (DATAv2, network-contracts OperatorTokenomics and StreamRegistry, and the network monorepo dht and trackerless-network packages), fetched raw files from GitHub, and read what is actually implemented. Contract addresses, entry points, the current token supply, and the live holders of MINTER_ROLE and DEFAULT_ADMIN_ROLE were verified directly against Ethereum mainnet and the published @streamr/config. Each claim below is labelled CONFIRMED IN CODE, OVERSTATED, or FALSE, with a repository path, file, line, and a short verbatim snippet.

## The Foundation: A Genuine 2017 Era Network That Shipped

**CLAIM:**
> Streamr is a decentralized real time data network where independent operators run nodes.

**REALITY:** CONFIRMED IN CODE. Unlike many projects we review, Streamr is not a fork or a wrapper. The `streamr-dev/network` monorepo is a from scratch peer to peer transport built around a Kademlia style distributed hash table (`@streamr/dht`) and a trackerless publish and subscribe overlay (`@streamr/trackerless-network`), with WebRTC and WebSocket connection layers. There is no central message broker in the data path. The on chain half lives in `streamr-dev/network-contracts` and is deployed on Polygon.

## Claim 1: A decentralized network with no central broker

**CLAIM:**
> "A decentralized network for real time data" in which nodes discover each other and route data peer to peer, without a central server.

**REALITY:** CONFIRMED IN CODE, with one honest caveat. The routing and discovery are genuinely peer to peer through the DHT and the trackerless overlay, and nodes connect directly (WebRTC or WebSocket). The caveat is bootstrap: the default published configuration seeds new nodes through two Streamr operated entry point servers. Entry points are overridable and any reachable node can act as one, so this is a convenience default rather than a hard dependency, but out of the box the first hop into the network is a Streamr controlled host.

**EVIDENCE:**
```jsonc
// @streamr/config config.json -> "polygon".entryPoints (the default bootstrap set)
[
  { "nodeId": "e5f87a7e...7596",
    "websocket": { "host": "polygon-entrypoint-3.streamr.network", "port": 443, "tls": true } },
  { "nodeId": "6f5b5381...852e",
    "websocket": { "host": "polygon-entrypoint-4.streamr.network", "port": 443, "tls": true } }

```
The DHT and overlay code (`packages/dht`, `packages/trackerless-network`) then take over for peer discovery and data delivery, so the entry points matter only for the initial join.

**IMPACT:** The data plane is genuinely decentralized and broker free. The only centralization is the default bootstrap seed, which is two `streamr.network` hosts. A self hosted operator can point at its own entry points, but the shipped default depends on Streamr infrastructure to join the mesh. Low.

## Claim 2: Operators stake DATA, and Sponsorships fund the network on chain

**CLAIM:**
> Operators run nodes and stake DATA; Sponsorships pay for streams to be relayed; delegators can delegate DATA to operators.

**REALITY:** CONFIRMED IN CODE. This is real, non trivial protocol engineering. `Sponsorship.sol` holds staked DATA (an ERC677 token), accepts sponsor top ups, and runs a pluggable policy set (join, allocation, leave, kick). `Operator.sol` is an ERC20 that mints operator tokens to delegators in exchange for DATA, tracks an exchange rate, and stakes the pooled DATA into Sponsorships. `OperatorFactory` and `SponsorshipFactory` deploy these permissionlessly.

## Claim 3: Misbehaving operators are slashed by decentralized peer voting

**CLAIM:**
> The network polices itself. Operators that go offline or misbehave are flagged, reviewed, and slashed.

**REALITY:** CONFIRMED IN CODE, and notably more decentralized than most projects we audit. `VoteKickPolicy.sol` implements a flag, review, vote, and resolve cycle. When an operator is flagged, a portion of the target stake is locked, a set of reviewers is drawn pseudo randomly from an on chain voter registry, reviewers vote during a fixed window, and the target is kicked and slashed only if the weighted vote crosses the threshold. No single admin performs the slash; it is the outcome of a peer vote enforced by the contract. A single reviewer weight is capped at half of total voter weight to blunt vote capture.

**EVIDENCE:**
```solidity
// network-contracts .../SponsorshipPolicies/VoteKickPolicy.sol
// onFlag(): lock target and flagger stake, then draw reviewers
// targetStakeAtRisk = max(stakedWei, minimumStakeWei) * slashingFraction / 1 ether
// reviewers randomly selected from the voter registry via a deterministic seed
// (flagger, target, and already-selected reviewers excluded)
// onVote(): weight = reviewer DATA value locked, capped to 50% of total voter weight
// _endVote(): tally; KICK if weighted votes pass threshold
// _handleKick():  reduce target locked stake by targetStakeAtRiskWei;
//                 pay flaggerRewardWei to flagger, reviewerRewardWei to kick voters,
//                 remainder to the protocol fee beneficiary
// _handleNoKick(): unlock target stake; slash the flagger to pay no-kick voters;
//                  grant the target a protection period against re flagging
```
```solidity
// Sponsorship.sol delegates the decision, it does not decide centrally:
function flag(...) external { moduleCall(address(kickPolicy), ... onFlag ...); } // L371-376
```

**IMPACT:** Positive and unusually strong. Slashing is not a hidden admin switch. It is a staked, incentivized, peer reviewed vote with anti capture caps and symmetric penalties (a frivolous flagger loses stake). This is genuine decentralized enforcement. Informational.

## Claim 4: Operators must post their own stake as skin in the game

**CLAIM:**
> Operators cannot run purely on other people's money; they have skin in the game and are slashed first.

**REALITY:** CONFIRMED IN CODE. `Operator.sol` requires the owner to hold a self delegation, and the code comments describe it verbatim as skin in the game that is burned on slashing. Delegators other than the owner are held to a `minimumDelegationWei`, and the docs enforce a 5 percent owner self stake and a 5,000 DATA global minimum to join Sponsorships.

**EVIDENCE:**

```solidity
//  operator gets slashed."

    if (delegator != owner) {

        if (balanceOf(delegator) < minimumDelegationWei) revert DelegationBelowMinimum(...);
    }
}
```
```
// docs.streamr.network (become-an-operator):
// "The owner (you) must have at least a 5% stake in the Operator."
// "there is a global minimum of 5k DATA tokens to join Sponsorships."
```

**IMPACT:** Positive. The economic alignment claim is real and enforced in the delegation accounting. Informational.

## Claim 5: Sponsorships pay publishers

**CLAIM:**
> "Sponsorships pay publishers" for the data they publish to the network.

**REALITY:** OVERSTATED as worded. Sponsorship earnings flow to the Operators who stake into a Sponsorship and relay the stream, not to the stream publisher. The typical flow is the reverse of the phrasing: a party who wants a stream carried (often the publisher or an interested third party) funds a Sponsorship, and node Operators earn from it by staking and doing the relaying work. The allocation policy pays stake weighted earnings to staked Operators, and the Streamr documentation states plainly that Sponsorships reward node operators.

**EVIDENCE:**
```solidity
// SponsorshipPolicies/StakeWeightedAllocationPolicy.sol
// earnings are allocated to staked operators in proportion to their stake and time,
// drawn from the Sponsorship's sponsored balance (remainingWei)
```
```
// docs.streamr.network (become-an-operator):
// "Join Sponsorships through your Operator that will earn you DATA tokens."
// anyone can call Sponsorship.sponsor(...) to fund the pot (Sponsorship.sol L162-168)
```

**IMPACT:** The mechanism is real and healthy, but the direction of payment in the slogan is inverted. Sponsorships are funded by whoever wants a stream carried and they pay the node Operators who carry it. A publisher who also runs an Operator can earn, but "Sponsorships pay publishers" is not how the contracts allocate. Medium.

## Claim 6: DATA has a fixed, community governed supply

**CLAIM:**
> The DATA supply is governed by the community, and market listings show a "max supply" of 2,000,000,000. New tokens are only minted "as decided by the community process" through Streamr Improvement Proposals.

**REALITY:** OVERSTATED. There is no supply cap anywhere in the token contract. `DATAv2.sol` exposes an unrestricted `mint(to, amount)` gated only by MINTER_ROLE, with no maximum and no per period limit. The "2,000,000,000 max supply" seen on market data sites is a marketing and listing figure, not a value the contract enforces. We verified on Ethereum mainnet that the current total supply is already 1,337,523,352 DATA, materially above the roughly 987 million minted for the original 2017 token, so additional minting has in fact happened. The MINTER_ROLE and the DEFAULT_ADMIN_ROLE that controls it are both held by a single contract that is a 2 of 6 Gnosis Safe multisig. The "community process" is a social convention (SIP votes), not an on chain constraint on the multisig.

**EVIDENCE:**
```solidity
// streamr-dev/DATAv2 contracts/DATAv2.sol
16  bytes32 constant public MINTER_ROLE = keccak256("MINTER_ROLE");
18  constructor() ERC20("", "") ERC20Permit(_name) {
19      _setupRole(DEFAULT_ADMIN_ROLE, _msgSender());   // admin can add/remove minters
20  }
25  function mint(address to, uint256 amount) public {
26      require(isMinter(_msgSender()), "Transaction signer is not a minter");
27      _mint(to, amount);                               // no cap, no rate limit
28  }
```
On chain verification (Ethereum mainnet, contract 0x8f693ca8...):

**IMPACT:** DATA is genuinely mintable and genuinely uncapped in code. Two of six multisig signers can mint arbitrary new DATA at will. That is better than a single private key and there is no evidence of abuse, but "fixed" or "2 billion max" is not enforced by the contract, and the dilution ceiling for holders is a social promise backed by a low signer threshold, not code. ## Claim 7: Anyone can create streams and run an operator, permissionlessly

**CLAIM:**
> Streamr is open and permissionless. Anyone can create a stream and anyone can run a node and become an Operator.

**REALITY:** CONFIRMED IN CODE, with a minor whitelist caveat on Operator policies. `StreamRegistry.createStream(...)` is a plain public function with no gate, and `OperatorFactory` lets anyone deploy an Operator. The caveat is that an Operator may only be wired with policy modules that an ADMIN_ROLE holder has added to a trusted policy whitelist, and the StreamRegistry carries a TRUSTED_ROLE that can set permissions for any user (used for metatransactions and ENS integration). Neither breaks open participation; they constrain which prebuilt modules an Operator uses and provide an admin permissioning helper.

**EVIDENCE:**
```solidity
// network-contracts .../StreamRegistry/StreamRegistryV5.sol
127 function createStream(string calldata streamIdPath, string calldata metadataJsonString) public {
128     _createStreamAndPermission(_msgSender(), addressToString(_msgSender()), streamIdPath, metadataJsonString);
129 }                                              // no role, no allowlist: fully permissionless
25  bytes32 public constant TRUSTED_ROLE = keccak256("TRUSTED_ROLE");   // can trustedSetPermissionsForUser
```
```solidity
// network-contracts .../OperatorTokenomics/OperatorFactory.sol
47  mapping(address => bool) public trustedPolicies;
99  function addTrustedPolicy(...)   onlyRole(ADMIN_ROLE)      // admin curates the module set
194 if (policyAddress != address(0) && !isTrustedPolicy(policyAddress)) revert PolicyNotTrusted();
```

**IMPACT:** Stream creation and Operator deployment are truly permissionless. The only gate is that Operators pick from an admin curated set of policy modules, which is a safety rail rather than a barrier to entry. Low to informational. Medium only in the sense that the module whitelist and TRUSTED_ROLE are admin powers worth disclosing.

## Claim 8: Trustless, no central control

**CLAIM:**
> The protocol is enforced by smart contracts; users do not have to trust a central operator.

**REALITY:** OVERSTATED. The tokenomics contracts are UUPS upgradeable and governed by roles, not immutable. `StreamrConfig` is the control panel for the whole staking economy, and a CONFIGURATOR_ROLE can change the protocol fee, the protocol fee beneficiary, the slashing fraction, the trusted forwarder, and the OperatorFactory and voter registry addresses. An ADMIN_ROLE grants those roles, and an UPGRADER_ROLE can replace the implementation. `OperatorFactory` and the registries are likewise upgradeable. As with the mint authority, this is standard for an upgradeable protocol, but it means the honest description is "governed by Streamr controlled roles," not "trustless and immutable."

**EVIDENCE:**
```solidity
// network-contracts .../OperatorTokenomics/StreamrConfig.sol  (UUPS)
uint    public protocolFeeFraction;                 // L111
address public protocolFeeBeneficiary;              // L113
uint    public slashingFraction;                    // L79
function setSlashingFraction(uint)      onlyRole(CONFIGURATOR_ROLE);   // ~L196 (must be < 1 ether)
function setProtocolFee...(...)         onlyRole(CONFIGURATOR_ROLE);   // ~L253-268
function setOperatorFactory(...)        onlyRole(CONFIGURATOR_ROLE);   // ~L328 (also sets voterRegistry)
function _authorizeUpgrade(address)     onlyRole(UPGRADER_ROLE);       // ~L346
// ADMIN_ROLE grants CONFIGURATOR_ROLE and UPGRADER_ROLE
```
```solidity
// OperatorFactory.sol   function _authorizeUpgrade(address) internal onlyRole(ADMIN_ROLE)   // L92
```

**IMPACT:** The staking contracts are not immutable and their fee and slashing parameters, plus the code itself, are changeable by role holders. This is normal upgradeable protocol governance and is mitigated by the same multisig style control as the token, but the accurate framing is "governed," not "trustless." Medium.

## Additional Note: The two power centers are the token multisig and the config roles

Worth stating plainly. Streamr's genuinely decentralized surfaces (peer to peer routing, permissionless streams and operators, peer voted slashing) sit on top of two centralized controls. First, uncapped DATA minting behind a 2 of 6 Gnosis Safe (Claim 6). Second, the StreamrConfig and factory upgrade and configuration roles that can retune fees and slashing and replace contract logic (Claim 8). Neither shows evidence of misuse, and the multisig plus SIP governance is a reasonable posture for a project of this age. But a user who reads "decentralized" and "fixed supply" literally should understand that supply and protocol parameters are, at the base layer, controlled by a small signer set.

## Conclusion

Streamr is a genuine, long running decentralized data network whose code substantially delivers what it markets. The peer to peer transport is real (Foundation, Claim 1). The on chain Operator staking, delegation, and Sponsorship economy is real and deployed (Claim 2). Slashing is enforced by an incentivized, anti capture peer vote rather than an admin switch, which is a stronger decentralization property than most projects we review can show (Claim 3). Operator self stake is real (Claim 4), and stream creation and Operator deployment are permissionless (Claim 7). Five claims are confirmed in code and none are false or fabricated.

The overstatements are the familiar gap between marketing language and governed reality. "Sponsorships pay publishers" inverts the actual flow: Sponsorships are funded by whoever wants a stream carried and paid out to the node Operators who carry it (Claim 5). "Fixed" or "2 billion max" supply is not enforced anywhere in the token, which exposes an uncapped `mint` behind a 2 of 6 multisig, and the live supply has already grown past the original 987 million to 1,337,523,352 DATA (Claim 6). "Trustless and immutable" is really an upgradeable, role governed protocol whose fees, slashing fraction, and logic can be changed by Streamr controlled roles (Claim 8).

None of this is fraud. It is the difference between a strong, working, genuinely decentralized data network and the frictionless, fixed supply, fully trustless narrative that the marketing occasionally implies. The one caveat that materially affects a token holder is the uncapped mint under a low threshold multisig. Score 82 out of 100, LOW to MEDIUM RISK, driven by that mint authority and by ordinary upgradeable protocol governance, not by any dishonest or broken code.
