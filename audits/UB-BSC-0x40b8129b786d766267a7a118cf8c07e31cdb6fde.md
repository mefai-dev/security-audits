## Why This Report Exists

## The Foundation: what Unibase actually is onchain

Unibase markets a stack of four things: Membase (agent memory), Unibase DA (data availability), the AIP interoperability protocol, and Unibase Pay (agent micropayments). The UB token is the asset attached to this story.

Onchain, the asset is simpler than the story. The Ethereum contract `0x6944...bcc8` is a plain ERC20 named UB with a fixed 10,000,000,000 supply, burnable, with no mint function and no owner. The BSC contract `0x40b8...6fde` is a LayerZero V2 Omnichain Fungible Token (contract `UBOFT`), an OpenZeppelin ERC20 plus Ownable plus the standard LayerZero OFT, verified byte for byte on Sourcify. The BSC contract holds about 1.945B UB, which is the portion that lives on BNB Chain within the omnichain design. The 10B figure the project markets is real and is anchored by the fixed Ethereum supply. There is no evidence of hidden inflation in the contracts themselves, with one caveat stated under Claim 3.

That is the whole onchain footprint of the token: a bridgeable ERC20. Everything else the project describes is offchain software plus a testnet.

## Claim 1: A decentralized data availability network, ZK verified, erasure coded, EB+ capacity, live on mainnet

CLAIM (docs): Unibase DA is "Data availability" that is "erasure-coded, ZK-verified, honest-one fraud proofs, EB+ capacity," and the docs state components are "Live on BNBChain Mainnet" with "SDKs, Docs, and Explorer fully released."

REALITY: OVERSTATED. A real Go client exists (`da-sdk-go`, about 328 commits) and it is organized around file, piece, and replica layers with Reed-Solomon erasure coding, which is genuine engineering. But it is explicitly a client SDK, and it points to a testnet gateway, `testnet.gateway.membase.io`. The actual node runtime, the onchain contracts, and the ZK proof system it references live in repositories `da-go`, `da-core`, and `da-contract`, and all three are not public (HTTP 404). The ZK verification, the fraud proofs, and the "EB+ capacity" are therefore unverifiable from source. Marketing says mainnet while the shipped SDK targets a testnet gateway, a direct tension.

EVIDENCE: `da-sdk-go` README references `testnet.gateway.membase.io` and names `da-go`, `da-core`, `da-contract` as the runtime and contract homes. Fetch of github.com/unibaseio/da-core returns 404. Org listing shows 37 public repos, none of which are the DA core.

IMPACT: The single most load bearing claim, a decentralized, cryptographically verifiable data layer, cannot be checked because the core is closed. A closed core with a testnet client is a prototype with a public wrapper, not a proven decentralized network. Credit is withheld for the unseen ZK, fraud proof, and capacity claims.

## Claim 2: A decentralized AI memory layer with wallet owned memory and onchain settlement

CLAIM (docs): Membase is an "Agent memory & collaboration SDK, wallet-owned encrypted memory, on-device recall, agent-direct cooperation, on chain settlement."

REALITY: OVERSTATED, with a real core of truth. The `membase` Python SDK is genuine, actively developed working code (about 62 commits, MIT license): it implements conversation memory buffers, Chroma vector storage for knowledge, long term memory summarization, and a `chain.py` module for agent registration and task permissions. So an SDK exists and does something. But the README does not demonstrate the decentralized, wallet owned, onchain settled properties the marketing asserts, it names no contract address, and it does not reference the UB token at all. The "decentralized" and "onchain settlement" adjectives are asserted, not shown, and the verification backend is not in public source.

EVIDENCE: github.com/unibaseio/membase README (features present, contract addresses and token references absent). aip-agent exists as a real interoperability protocol repo (Python, MIT).

IMPACT: There is a real product surface, which is why this is overstated rather than false. But a user cannot verify that memory is trustless or onchain settled from the public code, so the strongest decentralization language is unearned.

## Claim 3: The UB token powers the network (utility, staking, payments, governance)

CLAIM (marketing framing): UB is the asset of an "Open Agent Internet," an onchain agent economy with payments (Unibase Pay, x402) and settlement.

REALITY: FALSE / UNSUPPORTED in code. The BSC token contract is a stock LayerZero OFT with zero utility surface: no staking, no fee capture, no reward accrual, no governance, no payment routing, nothing that ties the token to Membase, DA, or Pay. The documentation does describe an extensive UB token economy (a Section 5 tokenomics with veUB vote escrowed governance, agent staking, knowledge mining, a ve(3,3) model, and DA staking with slashing and reward parameters), but none of it is implemented in any deployed contract. The public SDKs do not import or reference the token, and there is no public contract that consumes UB for staking, fees, or governance. In code the token is a bridgeable ERC20 and nothing more, so the promised economy is documented but entirely undelivered on chain, which is arguably a sharper concern at a multi billion dollar fully diluted valuation.

EVIDENCE: UBOFT ABI (functions are only ERC20, Ownable, and LayerZero OFT: `send`, `quoteSend`, `setPeer`, `setDelegate`, `setEnforcedOptions`, `setPreCrime`, `setMsgInspector`, `transferOwnership`, `renounceOwnership`, plus standard ERC20). Docs fetch: no UB utility, tokenomics, or supply content. membase README: no token reference.

Caveat on supply integrity: BSC minting is reachable only through `_credit`, which is called only from `_lzReceive` (the LayerZero endpoint delivery path). No owner mint exists. However, the owner (the Gnosis Safe) can call `setPeer`, and a peer is a trusted remote allowed to trigger mints on BSC. In the standard canonical plus adapter omnichain design, the 1.945B on BSC is backed by an equal amount locked on the Ethereum side, keeping global supply at 10B. I did not independently locate and verify the lock balance of that adapter, so the backing is consistent with the standard design but not independently proven here.

IMPACT: Price is supported by narrative and speculation rather than any demonstrated onchain demand for the token. At an FDV near $1.36B this is the central investor risk: a clean, safe token that the product does not yet need.

## Claim 4: The token is safe and fairly constructed

CLAIM (implicit): UB is a safe, standard token.

REALITY: CONFIRMED IN CODE. This is the strongest positive. The verified UBOFT source is a stock LayerZero V2 OFT over OpenZeppelin ERC20 and Ownable, with an empty derived constructor and no custom overrides. Concretely:
- No arbitrary mint. `_mint` is reached only via internal `_credit` from `_lzReceive`, gated by the LayerZero endpoint. Owner cannot mint.
- No transfer tax or fee. Default `_debitView` sets amountReceived equal to amountSent minus cross chain dust only, the source comment even contrasts this with a "10% fee" NON-default OFT that Unibase did not use. Same chain transfers use vanilla ERC20 `_update`.
- No pause: `paused()` reverts onchain. No blacklist function in the ABI. No max transaction or cooldown antibot gates.
- Not an upgradeable proxy: EIP-1967 implementation slot reads zero, and the runtime is a full contract, not a minimal proxy.
- Owner powers are limited to LayerZero configuration (`setPeer`, `setDelegate`, `setEnforcedOptions`, `setPreCrime`, `setMsgInspector`) plus ownership transfer or renounce, and the owner is a Gnosis Safe multisig rather than a single externally owned account.

EVIDENCE: `contracts/UBOFT.sol` (empty constructor body, no overrides); OFTCore `_debitView`, `_debit`, `_credit`, `_lzReceive` at lines 1487 to 1948 of the flattened source; onchain reverts for `paused()` and `getOwner()`; storage slot read for EIP-1967; owner account bytecode showing the Gnosis Safe masterCopy selector `0xa619486e`.

IMPACT: No honeypot, no rug primitive, no tax trap, no upgrade backdoor. The residual risk is the ordinary omnichain risk that a compromised or malicious owner sets a rogue peer to mint, mitigated but not eliminated by the multisig. This is a low risk token by construction.

## Positive Findings

- Token contract is clean and verified. Standard LayerZero OFT, Sourcify exact match, no mint, no tax, no pause, no blacklist, not upgradeable.
- Owner is a Gnosis Safe multisig, not a lone key, and ownership powers are confined to bridge configuration.
- Ethereum supply is a fixed 10B with no mint and no owner, a credible hard cap anchor.
- Real, actively maintained public client code exists (membase, membase-mcp, aip-agent, da-sdk-go), including genuine erasure coding and vector memory engineering.
- Deep, liquid, actively traded market with a top 120 rank. The asset is live.

## Conclusion

Unibase is a legitimate, live, actively traded BNB Chain project with a clean, verified, low risk token and a real, shipping software surface. On those axes the earlier score of 20 badly understated it. But the flagship claim, a decentralized and cryptographically verifiable data availability and memory network, cannot be verified because the core (da-core, da-go, da-contract) is private and the shipped DA client targets a testnet, and the UB token has no demonstrated onchain utility in either the contract or the documentation. So the project is neither a fraud nor the verifiable decentralized infrastructure it markets. It is a well built, safe token wrapped around a partly open, partly closed prototype, carrying a rich narrative and a rich valuation that the onchain token does not yet justify. Score 63 out of 100, MEDIUM RISK, Passed, with the passing grade resting on token safety and liveness, and the ceiling set by the closed core and the absent token utility. Where the core is closed, no credit is given for the unseen.
